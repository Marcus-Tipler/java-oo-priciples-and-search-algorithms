The Strategy Pattern is a behavioural design pattern that lets a program choose between different algorithms or behaviours at runtime.

Instead of putting every possible behaviour into one large class with many `if` or `switch` statements, each behaviour is placed in its own class behind a shared interface.

A useful way to think about it is:

> “Here is the job that needs doing. I can plug in different ways of doing that job.”

## Basic structure

The pattern normally has three parts:

1. **Strategy interface** — defines the operation.
2. **Concrete strategies** — provide different implementations.
3. **Context** — uses a strategy without needing to understand its implementation.

```text
Context ──uses──> Strategy
                   ├── StrategyA
                   ├── StrategyB
                   └── StrategyC
```

## Example: command-line calculator

Suppose we want a calculator that supports addition, subtraction, multiplication, and division. Each calculation can be represented as a strategy.

Save this as `StrategyCalculator.java`:

```java
import java.util.Scanner;

public class StrategyCalculator {

    // The strategy interface
    interface CalculationStrategy {
        double calculate(double first, double second);
    }

    // Concrete strategies
    static class AdditionStrategy implements CalculationStrategy {
        @Override
        public double calculate(double first, double second) {
            return first + second;
        }
    }

    static class SubtractionStrategy implements CalculationStrategy {
        @Override
        public double calculate(double first, double second) {
            return first - second;
        }
    }

    static class MultiplicationStrategy implements CalculationStrategy {
        @Override
        public double calculate(double first, double second) {
            return first * second;
        }
    }

    static class DivisionStrategy implements CalculationStrategy {
        @Override
        public double calculate(double first, double second) {
            if (second == 0) {
                throw new IllegalArgumentException("Cannot divide by zero.");
            }

            return first / second;
        }
    }

    // The context
    static class Calculator {
        private CalculationStrategy strategy;

        public void setStrategy(CalculationStrategy strategy) {
            this.strategy = strategy;
        }

        public double calculate(double first, double second) {
            if (strategy == null) {
                throw new IllegalStateException(
                    "A calculation strategy has not been selected."
                );
            }

            return strategy.calculate(first, second);
        }
    }

    public static void main(String[] args) {
        Scanner scanner = new Scanner(System.in);
        Calculator calculator = new Calculator();

        System.out.print("Enter the first number: ");
        double first = scanner.nextDouble();

        System.out.print("Choose an operation (+, -, *, /): ");
        String operation = scanner.next();

        System.out.print("Enter the second number: ");
        double second = scanner.nextDouble();

        CalculationStrategy selectedStrategy = switch (operation) {
            case "+" -> new AdditionStrategy();
            case "-" -> new SubtractionStrategy();
            case "*" -> new MultiplicationStrategy();
            case "/" -> new DivisionStrategy();
            default -> throw new IllegalArgumentException(
                "Unknown operation: " + operation
            );
        };

        calculator.setStrategy(selectedStrategy);

        try {
            double result = calculator.calculate(first, second);
            System.out.println("Result: " + result);
        } catch (IllegalArgumentException exception) {
            System.out.println("Error: " + exception.getMessage());
        } finally {
            scanner.close();
        }
    }
}
```

Compile and run it:

```bash
javac StrategyCalculator.java
java StrategyCalculator
```

Example session:

```text
Enter the first number: 12
Choose an operation (+, -, *, /): *
Enter the second number: 4
Result: 48.0
```

## Where is the pattern?

The strategy is the interface:

```java
interface CalculationStrategy {
    double calculate(double first, double second);
}
```

Each concrete strategy supplies one calculation:

```java
class AdditionStrategy implements CalculationStrategy {
    @Override
    public double calculate(double first, double second) {
        return first + second;
    }
}
```

The `Calculator` is the context. Notice that it does not contain addition, subtraction, or division logic:

```java
return strategy.calculate(first, second);
```

It only knows that the selected object satisfies the `CalculationStrategy` contract.

The strategy is selected at runtime based on the user's input:

```java
CalculationStrategy selectedStrategy = switch (operation) {
    case "+" -> new AdditionStrategy();
    case "-" -> new SubtractionStrategy();
    // ...
};
```

A small `switch` is still present, but its only job is selecting an object. The actual algorithms are not tangled inside the switch.

## Changing strategies while the program runs

Strategies are ordinary objects, so the context can switch between them:

```java
Calculator calculator = new Calculator();

calculator.setStrategy(new AdditionStrategy());
System.out.println(calculator.calculate(10, 5)); // 15.0

calculator.setStrategy(new MultiplicationStrategy());
System.out.println(calculator.calculate(10, 5)); // 50.0
```

The same `Calculator` object now exhibits different behaviour.

## A more realistic example: delivery charges

A shopping program might offer several delivery calculations:

```java
interface DeliveryStrategy {
    double calculateCost(double orderValue);
}

class StandardDelivery implements DeliveryStrategy {
    @Override
    public double calculateCost(double orderValue) {
        return orderValue >= 50 ? 0 : 4.99;
    }
}

class ExpressDelivery implements DeliveryStrategy {
    @Override
    public double calculateCost(double orderValue) {
        return 9.99;
    }
}

class StoreCollection implements DeliveryStrategy {
    @Override
    public double calculateCost(double orderValue) {
        return 0;
    }
}
```

The checkout process can accept any delivery strategy:

```java
class Checkout {
    private final DeliveryStrategy deliveryStrategy;

    public Checkout(DeliveryStrategy deliveryStrategy) {
        this.deliveryStrategy = deliveryStrategy;
    }

    public double calculateTotal(double orderValue) {
        return orderValue + deliveryStrategy.calculateCost(orderValue);
    }
}
```

Example usage:

```java
DeliveryStrategy delivery = new ExpressDelivery();
Checkout checkout = new Checkout(delivery);

System.out.println(checkout.calculateTotal(40)); // 49.99
```

This design makes it easy to add something like `InternationalDelivery` without modifying `Checkout`.

## Using lambdas in modern Java

If the strategy interface has exactly one abstract method, it is a functional interface and can be implemented with a lambda:

```java
@FunctionalInterface
interface DiscountStrategy {
    double apply(double price);
}
```

Strategies can then be written without separate classes:

```java
DiscountStrategy noDiscount = price -> price;
DiscountStrategy studentDiscount = price -> price * 0.90;
DiscountStrategy halfPrice = price -> price * 0.50;

System.out.println(studentDiscount.apply(100)); // 90.0
```

Named classes are often clearer when strategies contain substantial logic or dependencies. Lambdas are convenient for small, self-contained behaviours.

## When the Strategy Pattern is useful

Use it when:

- A task can be performed in several interchangeable ways.
- You want to select an algorithm at runtime.
- A class contains a growing collection of behavioural `if` or `switch` branches.
- You expect new behaviours to be added over time.
- You want to test each algorithm independently.

Common examples include:

- Payment methods
- Discounts and tax calculations
- Sorting or searching algorithms
- Route-planning algorithms
- File compression formats
- Validation rules
- Authentication methods
- Logging and notification mechanisms

It may be unnecessary when there are only two extremely small behaviours that are unlikely to change. In that case, introducing several interfaces and classes could add more structure than value.

The pattern’s central idea is simple: **encapsulate each varying algorithm behind a common interface, then supply the desired algorithm to the object that needs it.**

## Strategy-based module search

First, define the shared strategy:

```java
import java.util.List;

interface ModuleSearchStrategy {
    List<StudentModule> search(
        List<StudentModule> modules,
        String searchTerm
    );
}
```

The module model:

```java
record StudentModule(
    String moduleCode,
    String title,
    String description
) {}
```

Then provide different strategies.

### Search by title

```java
class SearchByTitle implements ModuleSearchStrategy {

    @Override
    public List<StudentModule> search(
        List<StudentModule> modules,
        String searchTerm
    ) {
        return modules.stream()
            .filter(module ->
                module.title().toLowerCase()
                    .contains(searchTerm.toLowerCase())
            )
            .toList();
    }
}
```

### Search by module code

```java
class SearchByModuleCode implements ModuleSearchStrategy {

    @Override
    public List<StudentModule> search(
        List<StudentModule> modules,
        String searchTerm
    ) {
        return modules.stream()
            .filter(module ->
                module.moduleCode().equalsIgnoreCase(searchTerm)
            )
            .toList();
    }
}
```

### Search by description

```java
class SearchByDescription implements ModuleSearchStrategy {

    @Override
    public List<StudentModule> search(

        String searchTerm
    ) {
        return modules.stream()
            .filter(module ->
                module.description().toLowerCase()
```

## The search service

This is the context that uses the selected strategy:

```java
class ModuleSearchService {

    private ModuleSearchStrategy strategy;

    public void setStrategy(ModuleSearchStrategy strategy) {
        this.strategy = strategy;
    }

    public List<StudentModule> search(
        List<StudentModule> modules,
        String searchTerm
    ) {
        if (strategy == null) {
            throw new IllegalStateException(
                "No search strategy has been selected."
            );
        }

        return strategy.search(modules, searchTerm);
    }
}
```

```java
public class ModuleSearchApplication {
```

## Connecting it to a real database

With a database, each strategy could execute a different parameterised SQL query:

```java
interface ModuleSearchStrategy {
    List<StudentModule> search(
        Connection connection,
        String searchTerm
    ) throws SQLException;
}
```

A title strategy might look like this:

```java
class SearchByTitle implements ModuleSearchStrategy {

    private static final String SQL = """
        SELECT module_code, title, description
        FROM student_module
        WHERE LOWER(title) LIKE LOWER(?)
        """;

    @Override
    public List<StudentModule> search(
        Connection connection,
        String searchTerm
    ) throws SQLException {
        List<StudentModule> results = new ArrayList<>();

        try (PreparedStatement statement =
                 connection.prepareStatement(SQL)) {

            statement.setString(1, "%" + searchTerm + "%");

            try (ResultSet resultSet = statement.executeQuery()) {
                while (resultSet.next()) {
                    results.add(new StudentModule(
                        resultSet.getString("module_code"),
                        resultSet.getString("title"),
                        resultSet.getString("description")
                    ));
                }
            }
        }

        return results;
    }
}
```

Using `PreparedStatement` is important because search text should not be inserted directly into SQL strings.

## Searching every field

You could add another strategy that looks in all three fields:

```java
class SearchAllFields implements ModuleSearchStrategy {

    @Override
    public List<StudentModule> search(
        List<StudentModule> modules,
        String searchTerm
    ) {
        String term = searchTerm.toLowerCase();

        return modules.stream()
            .filter(module ->
                module.moduleCode().toLowerCase().contains(term)
                    || module.title().toLowerCase().contains(term)
                    || module.description().toLowerCase().contains(term)
            )
            .toList();
    }
}
```

This is still a valid strategy because “search all fields” is one complete search policy.

## What if conditions need to be combined?

Suppose the user supplies:

```text
Title contains: Java
Module code starts with: CS
Description contains: patterns
```

Creating a separate strategy for every combination quickly becomes awkward:

```text
SearchByTitleAndCode
SearchByTitleAndDescription
SearchByCodeAndDescription
SearchByTitleAndCodeAndDescription
```

For this, composable predicates are more appropriate:

```java
import java.util.function.Predicate;

Predicate<StudentModule> titleContains(String value) {
    String term = value.toLowerCase();

    return module ->
        module.title().toLowerCase().contains(term);
}

Predicate<StudentModule> codeStartsWith(String value) {
    String term = value.toLowerCase();

    return module ->
        module.moduleCode().toLowerCase().startsWith(term);
}
```

Conditions can then be combined:

```java
Predicate<StudentModule> condition =
    titleContains("Java")
        .and(codeStartsWith("CS"));

List<StudentModule> results = modules.stream()
    .filter(condition)
    .toList();
```

The practical design rule is:

- Use **Strategy** to choose the overall search method.
- Use **predicates/specifications** to build combinations of conditions.
- Both can be used together: a strategy might translate a collection of conditions into SQL.
- For a production database, add appropriate indexes; broad `%term%` searches often need database full-text search for good performance.
