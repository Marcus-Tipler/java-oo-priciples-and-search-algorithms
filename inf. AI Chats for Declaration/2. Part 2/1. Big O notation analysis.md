The main searching algorithms in this class are currently **linear time: `O(n)`**, because both search methods iterate through every module in the `modules` list.

Here’s the breakdown:

| Method | Time Complexity | Why |
|---|---:|---|
| `addModule()` | **O(1)** amortized | `ArrayList.add()` normally appends directly to the end |
| `searchByYearAndSubject()` | **O(n)** | Iterates through all `n` modules |
| `searchByKeyword()` | **O(n)** in terms of modules | Iterates through all `n` modules |
| Storage | **O(n)** | Stores `n` modules |

### `searchByYearAndSubject()`

```java
for (OptionalModule module : modules) {
    if (module.getYear() == year &&
        module.getSubjectArea().equalsIgnoreCase(subjectArea)) {
        results.add(module);
    }
}
```

If there are **n modules**, the loop checks every module once.

So:

\[
\boxed{O(n)}
\]

Importantly, even if it finds a matching module immediately, it **doesn't stop**, because there may be multiple matching modules. Therefore:

- Best case: **O(n)**
- Average case: **O(n)**
- Worst case: **O(n)**

### `searchByKeyword()`

This is also fundamentally:

\[
\boxed{O(n)}
\]

because of:

```java
for (OptionalModule module : modules)
```

However, there's a little more going on inside the loop:

```java
module.getCode().toLowerCase().contains(...)
module.getName().toLowerCase().contains(...)
module.getSubjectArea().toLowerCase().contains(...)
```

String searching itself isn't technically constant time. If we let **m** represent the average length of the strings being searched, a more precise analysis would be approximately:

\[
\boxed{O(nm)}
\]

because you're doing string operations for each of the `n` modules.

For coursework purposes, though, if you're analysing performance based primarily on the **number of modules**, calling this **O(n)** is normally appropriate.

### One inefficiency worth fixing

This code:

```java
keyword.toLowerCase()
```

gets recalculated repeatedly for every module and potentially several times per module.

You could instead do:

```java
public List<OptionalModule> searchByKeyword(String keyword) {
    List<OptionalModule> results = new ArrayList<>();

    String normalizedKeyword = keyword.toLowerCase();

    for (OptionalModule module : modules) {
        if (module.getCode().toLowerCase().contains(normalizedKeyword) ||
            module.getName().toLowerCase().contains(normalizedKeyword) ||
            module.getSubjectArea().toLowerCase().contains(normalizedKeyword)) {
            results.add(module);
        }
    }

    return results;
}
```

That **doesn't change the Big-O complexity**—it remains `O(n)` with respect to the number of modules—but reduces unnecessary work.

### The bigger algorithmic issue

At the moment your catalogue is essentially:

```text
ArrayList
   ↓
Module 1
Module 2
Module 3
Module 4
...
Module n
```

Every query performs a **linear scan**:

```text
Search request
     ↓
[1] → [2] → [3] → [4] → ... → [n]
                              
             O(n)
```

If this is for your **Algorithms and Data Structures coursework**, there's quite a good opportunity here to demonstrate improvement by introducing an appropriate data structure.

For example, `searchByYearAndSubject()` could potentially use a `HashMap`-based index:

```java
Map<ModuleKey, List<OptionalModule>>
```

where something like:

```java
ModuleKey(year, subjectArea)
```

acts as the key.

Then retrieving modules for an exact year/subject combination could be approximately:

\[
\boxed{O(1)}
\]

average lookup time, rather than:

\[
O(n)
\]

That would give you a very clear **before/after algorithmic-complexity comparison** to discuss in your coursework.
